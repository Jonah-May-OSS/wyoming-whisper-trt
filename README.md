# Wyoming Whisper TRT

Runs [OpenAI Whisper](https://github.com/openai/whisper) on [NVIDIA TensorRT](https://developer.nvidia.com/tensorrt)
and serves it over the [Wyoming protocol](https://www.home-assistant.io/integrations/wyoming/)
for Home Assistant.

On a Jetson Orin Nano, `base.en` runs **~3x faster** on **~60%** the memory
compared with PyTorch. The API roughly mimics the original Whisper model; the
Wyoming server is [wyoming-faster-whisper](https://github.com/rhasspy/wyoming-faster-whisper)
with minimal tweaks to use WhisperTRT instead of faster-whisper.

Originally built for the Jetson Orin Nano, now developed in Docker on x86
Ubuntu 24.04 with a 4070 Ti.

## Performance

Transcribing a 20-second clip, generated by
[profile_backend.py](examples/profile_backend.py).

**Execution time**

|         | whisper (Jetson) | faster_whisper (Jetson) | whisper_trt (Jetson) | whisper (4070 Ti) | faster_whisper (4070 Ti) | whisper_trt (4070 Ti) |
|---------|------------------|-------------------------|----------------------|-------------------|--------------------------|-----------------------|
| tiny.en | 1.74 s           | 0.85 s                  | **0.64 s**           | 0.40 s            | 0.35 s                   | **0.07 s**            |
| base.en | 2.55 s           | Unavailable             | **0.86 s**           | 0.71 s            | 0.34 s                   | **0.10 s**            |

**Memory consumption**

|         | whisper (Jetson) | faster_whisper (Jetson) | whisper_trt (Jetson) | whisper (4070 Ti) | faster_whisper (4070 Ti) | whisper_trt (4070 Ti) |
|---------|------------------|-------------------------|----------------------|-------------------|--------------------------|-----------------------|
| tiny.en | 569 MB           | **404 MB**              | 488 MB               | 672 MB            | **522 MB**               | 544 MB                |
| base.en | 666 MB           | Unavailable             | **439 MB**           | 726 MB            | **514 MB**               | 548 MB                |

> Every VRAM figure in this README was measured before engine-scratch pooling
> landed, so it overstates what the `kv` decoder reserves today. Treat them as
> upper bounds.

## Requirements

1. Docker 23 or newer.
2. The [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html).
3. Docker's containerd image store. The published images use zstd-compressed
   layers, which the classic store cannot pull — the symptom is
   `unsupported media type application/vnd.oci.image.layer.v1.tar+zstd`. Merge
   this into `/etc/docker/daemon.json` and restart the daemon:

   ```json
   {
     "features": {
       "containerd-snapshotter": true
     }
   }
   ```

   Add the key to your existing `"features"` object rather than replacing it.
   Docker Desktop 4.34+ and fresh Docker Engine 29+ installs already have this
   on; upgraded installs must opt in. JetPack 5 ships Docker 20.10, which
   cannot pull these images at all — build locally from the Dockerfile.

ARM64 containers may take a while to start on first launch after an install or
update. I do not have ARM64 or Jetson hardware, so packages such as torch and
torch2trt fail to install properly under QEMU/buildx because CUDA is not
detected. If you know how to get around this, please reach out.

### Which image for a Jetson?

| JetPack | Image |
|---|---|
| 6.x (L4T r36) | `captnspdr/wyoming-whisper-trt:latest-igpu` |
| 7.2+ (L4T r39.2) | `captnspdr/wyoming-whisper-trt:latest` (the standard ARM64 image) |

JetPack 7.2 aligns Orin with the SBSA baseline, so a Jetson on r39.2 runs
mainstream ARM64 containers directly and the `-igpu` tag is no longer needed.
(7.2 is the first 7.x release covering the Orin family; 7.0 and 7.1 are
Thor-only.)

The `-igpu` image is JetPack 6 only. On JetPack 7 it loops on startup with
`ImportError: libnvdla_compiler.so: cannot open shared object file`. That
library was dropped in JetPack 7 and cannot be installed; the fix is the
standard image, not a workaround.

The JetPack 7 path is confirmed working on an Orin Nano 8 GB (JetPack 7.2,
L4T R39.2.0): CUDA available, engine builds, transcription TensorRT-accelerated.
Torch prints one harmless startup warning about `sm_87` not being in its
published build list — CUDA runs `sm_80` code on any 8.x GPU, so it costs
nothing.

## Installation

### Docker Compose (recommended)

For discrete GPUs (AMD64 or ARM64):

```yaml
services:
  wyoming-whisper-trt:
    image: captnspdr/wyoming-whisper-trt:latest
    container_name: wyoming-whisper-trt
    ports:
      - 10300:10300
    restart: unless-stopped
    environment:
      MODEL: "${MODEL:-base}"
      LANGUAGE: "${LANGUAGE:-auto}"
      URI: "${URI:-tcp://0.0.0.0:10300}"
      DATA_DIR: "${DATA_DIR:-/data}"
      COMPUTE_TYPE: "${COMPUTE_TYPE:-float16}"
      DECODER_MODE: "${DECODER_MODE:-kv}"
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
```

For a Jetson iGPU on JetPack 6, use the `latest-igpu` image, drop the `deploy:`
block in favour of `network_mode: host` and `runtime: nvidia`, and add three
entries to the same `environment:` block:

```yaml
      NVIDIA_VISIBLE_DEVICES: all
      NVIDIA_DRIVER_CAPABILITIES: compute,utility
      # Required on Jetson. run.sh keys its first-run setup off this: without
      # it, setup installs the x86 torch/TensorRT pins from requirements.txt
      # over JetPack's own builds and the container fails to start.
      NVIDIA_EMBEDDED: "true"
```

[docker-compose-igpu.yaml](docker-compose-igpu.yaml) in the repository is this
file, ready to run.

### docker run

```bash
docker run \
  --gpus all \
  --name wyoming-whisper-trt \
  -d \
  -p 10300:10300 \
  -v whisper-trt-data:/data \
  -e MODEL=base \
  -e LANGUAGE=auto \
  -e COMPUTE_TYPE=float16 \
  -e DECODER_MODE=kv \
  captnspdr/wyoming-whisper-trt:latest
```

The `/data` volume holds downloaded weights and built engines. Without it,
every container start rebuilds the TensorRT engines from scratch.

A JetPack 6 Jetson needs more than a different image — `--runtime nvidia`,
host networking and `NVIDIA_EMBEDDED=true` as well — so use
[docker-compose-igpu.yaml](docker-compose-igpu.yaml) rather than adapting the
command above. `int8` is unavailable there; use `float16`.

### Building from the latest commit

Clone the repository, then from its root:

```bash
docker compose -f docker-compose-github.yaml up -d       # dGPU, ARM64 or AMD64
docker compose -f docker-compose-github-igpu.yaml up -d  # Jetson iGPU
```

## Configuration

### Environment variables

| Variable | Default | Description |
|---|---|---|
| `MODEL` | `base` | Which model to load. See [Supported models](#supported-models). |
| `LANGUAGE` | `auto` | Transcription language, e.g. `en`, `es`. Read [Limitations](#limitations) before relying on `auto`. |
| `URI` | `tcp://0.0.0.0:10300` | Address the Wyoming server binds to. |
| `DATA_DIR` | `/data` | Where weights are downloaded and engines are cached. |
| `COMPUTE_TYPE` | `float16` | `float32`, `float16` or `int8`. See [Compute types](#compute-types-and-int8). |
| `DECODER_MODE` | `kv` | `kv` or `simple`. See [Decoder modes](#decoder-modes). |
| `NO_SPEECH_THRESHOLD` | `0.6` | See [Silence hallucination suppression](#silence-hallucination-suppression). |
| `SILENCE_THRESHOLD` | `0.0` | As above; `0.0` disables the energy gate. |

Those are the only variables the entrypoint reads. Every other server flag is
set by appending arguments to the container command, which the entrypoint
forwards — `--no-cuda-graphs`, `--initial-prompt`, `--max-workspace-mb`,
`--streaming` and `--debug` have no environment variable of their own:

```yaml
    command: ["--debug", "--initial-prompt", "Living room, kitchen, hallway."]
```

Run `--help` for the full list:

```bash
docker run --rm --entrypoint python3 captnspdr/wyoming-whisper-trt:latest \
  -m wyoming_whisper_trt --help
```

### Supported models

Only the official OpenAI models from HuggingFace are supported. Quantized or
otherwise modified variants are not.

**Multilingual** — `tiny`, `base`, `small`, `medium`, `large`, `large-v2`,
`large-v3`, `large-v3-turbo`

**English only** — `tiny.en`, `base.en`, `small.en`

### Limitations

**Single 30 s window.** Whisper's encoder operates on a fixed 30-second window,
and WhisperTRT transcribes exactly one window per request: longer audio is
truncated to the first 30 s, with no sliding-window chunking. This suits the
short utterances Home Assistant sends; it is not a long-form transcription
backend.

**`LANGUAGE=auto` is effectively English.** Upstream `whisper.transcribe` runs
a dedicated language-detection pass and prepends the detected `<|lang|>` token
to the decoder prompt. WhisperTRT does not run that pass, so in `auto` mode no
language token is injected, decoding is unsteered, and it is strongly biased
toward English. Set `LANGUAGE` explicitly for reliable non-English
transcription. English-only models (`*.en`) always transcribe English
regardless.

## Tuning

### Decoder modes

Decoding is autoregressive — the text decoder runs once per output token — so
its implementation drives latency.

- **`kv`** (default): caches self-attention key/values across steps and
  projects cross-attention K/V once per utterance, across three TensorRT
  engines. Fastest.
- **`simple`**: a single engine that recomputes the whole token prefix each
  step. One set of decoder weights rather than three, so it uses less VRAM.

Measured on `base`, 300 utterances, float16, RTX 3050, TensorRT 10:

| | `kv` (default) | `simple` |
|---|---|---|
| WER | 5.37 % | 5.36 % |
| Latency p95 | 0.124 s | 0.144 s |
| Latency mean | 0.058 s | 0.068 s |
| Realtime factor | 128× | 110× |
| VRAM (nvidia-smi) | 1032 MiB | 834 MiB |
| Decoder engine(s) | 95.9 MiB (3) | 51.0 MiB (1) |

`kv` is ~14 % faster; `simple` uses ~200 MiB less VRAM. Both run well over 100×
realtime, so `simple` is a reasonable trade on tight-VRAM devices.

Engine *scratch* is no longer part of that difference: all of a checkpoint's
engines share one device-memory pool sized to the largest, since only one runs
at a time (where TensorRT supports application-managed context memory;
elsewhere each engine keeps a private pool). What `simple` still saves is the
duplicated decoder weights, which is what matters on the large family.

Most of WhisperTRT's decode speedup comes from optimizations that apply to
*both* modes — final-position projection, GPU-side mel, fewer host syncs. The
KV cache itself is the last ~14 %.

### CUDA graph replay

With `DECODER_MODE=kv`, the per-token decoder step is captured into a CUDA
graph and replayed rather than re-launched kernel by kernel. The decode loop is
host-launch-bound, so this roughly halves per-step time and tightens the p99
tail. It is on by default; `--no-cuda-graphs` restores the dynamic step engine.

Two things worth knowing:

- Toggling it selects a different step engine, so each setting builds and
  caches its own checkpoint.
- If capture fails on your driver and TensorRT combination, the decoder falls
  back to running the step directly. Transcription stays correct; only the
  launch saving is lost.

It has no effect with `DECODER_MODE=simple`, whose engine changes shape every
token.

### Compute types and int8

`COMPUTE_TYPE=int8` quantizes the audio encoder's convolutions and matmuls to
INT8 and leaves everything else — layer norms, softmax, and the whole text
decoder — in FP16. Quantization is *explicit*: after the encoder is exported to
ONNX, [NVIDIA ModelOpt](https://github.com/NVIDIA/TensorRT-Model-Optimizer)
rewrites the graph with Q/DQ pairs calibrated on real speech mels — from the
clips in `whisper_trt/calibration/`, so add your own 16 kHz mono WAVs there to
widen acoustic coverage — and casts the remainder to FP16 in the same pass.
Graph inputs and outputs stay FP32, so nothing changes at the runtime boundary.

Calibration replays the graph through onnxruntime on the **CPU** (the image
ships CPU-only onnxruntime), so an int8 build costs roughly one CPU encoder
pass per calibration clip on top of a float16 build — noticeable on
`medium`/`large`.

**Why explicit.** TensorRT 11 removed implicit quantization, where the builder
ran a calibrator and then used INT8 only where it timed faster than FP16. That
removal also fixed a genuine surprise on TensorRT 10: an int8 engine could come
out byte-for-byte equivalent to float16. Measured on `base` over 300 utterances
(RTX 3050), the implicit int8 build matched float16 on every axis — 5.37 % WER,
0.124 s p95, 1032 MiB VRAM, a ~40 MiB encoder engine — because **0 of its 105
layers actually ran in INT8**. No INT8 tactic won on timing, so the builder
chose FP16 everywhere and "int8" was float16 with extra build steps. Q/DQ pairs
are honoured regardless of tactic timings, so INT8 now actually takes.

`int8` is x86/dGPU only. The Jetson iGPU image runs against JetPack's own
TensorRT and PyTorch, which are too old for ModelOpt, so it installs without it
and `COMPUTE_TYPE=int8` fails with an explanatory error — use `float16`.

It remains a speed/accuracy trade rather than a free win, and it has **not**
been re-measured on the explicit path. INT8 activations cost accuracy that only
your own audio can quantify, and small encoders may not be FLOP-bound enough to
gain. Measure on your own hardware before running it in production — see
[Benchmarking](#benchmarking).

### Silence hallucination suppression

Fed audio with no real speech, Whisper reliably invents plausible-looking text
— `www.mooji.org`, `Thank you for watching`, subtitle credits — pulled from its
training data. Greedy decoding never selects the model's `<|nospeech|>` token,
because a real token always outscores it, so without a guard those phantom
transcripts flow straight through to Home Assistant.

Two gates suppress them:

- **No-speech gate** (`NO_SPEECH_THRESHOLD`, default `0.6`): drops a window
  whose `<|nospeech|>` probability at the first decode position is at or above
  the threshold, exactly as upstream `whisper.transcribe` does. This is the
  accurate check and is on by default. Set it above `1.0` to disable.
- **Energy gate** (`SILENCE_THRESHOLD`, default `0.0` = disabled): an optional
  cheap hard cutoff that skips transcription when the audio's normalized
  ([-1, 1]) RMS is below the threshold. Useful as belt-and-braces, but it can
  clip genuinely quiet speech, so it is off unless you opt in (e.g. `0.005`).

Both make the server emit an empty transcript, which Home Assistant handles as
"nothing was said".

### Low-resource and edge devices

Most of the runtime footprint is the fixed CUDA/cuDNN context rather than the
weights — the TensorRT engines for `base` total only tens of MiB — so model
choice and decoder mode are the levers that actually move VRAM.

- **`MODEL=tiny.en`** — the smallest English model. Substantially faster and
  leaner than `base.en` at some WER cost. For the short, limited-vocabulary
  utterances Home Assistant sends this is often more than adequate; move up
  only if you see commands mis-heard.
- **`DECODER_MODE=simple`** — ~200 MiB less VRAM for ~14 % higher latency. See
  [Decoder modes](#decoder-modes).
- **`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`** — an optional,
  low-risk allocator setting that can reduce reserved-but-unused VRAM from
  fragmentation. The effect on a steady inference workload is modest, but it
  costs nothing to enable.

The large family (`large`, `large-v2`, `large-v3`, `large-v3-turbo`) is a
different proposition from `base` and the ratios above do not carry over. Its
weights dominate, and in `kv` mode the decoder is three engines each carrying
their own copy of the decoder weights, so resident VRAM lands at several times
the FP16 weight size — tight next to another GPU tenant on a 16 GB card. If you
are sharing the GPU with an LLM, `DECODER_MODE=simple` is the one lever that
removes weight copies rather than merely scratch.

### Build-time workspace

`--max-workspace-mb` is **not** a runtime VRAM lever. It caps the scratch
TensorRT may use while *searching tactics during the build*, and has no effect
on what a loaded engine reserves. Lowering it to save runtime VRAM only risks
worse tactics and a rebuild.

Its one legitimate use is escaping a build that runs out of memory. TensorRT
reports that as `Could not find any implementation for node ...`, which reads
like an unsupported-operation problem — but the graph is fine; there was simply
not enough memory for the tactic search. The budget is re-clamped against free
VRAM before each engine, so this should be rare. If you still hit it, try a
smaller `MODEL`, `DECODER_MODE=simple`, or a lower `--max-workspace-mb`.

## Development

guidelines. The repository also includes [Copilot instructions](.github/copilot-instructions.md)

### Quick start

```bash
git clone --recursive https://github.com/Jonah-May-OSS/wyoming-whisper-trt.git
cd wyoming-whisper-trt

python script/setup --dev   # create the venv and install dev dependencies
python script/format        # format
python script/lint          # ruff + ty
python script/test          # pytest
```

### Testing and linting

- **[Ruff](https://github.com/astral-sh/ruff)** — linting, formatting and
  import sorting, replacing black, isort, flake8 and pylint.
- **[ty](https://github.com/astral-sh/ty)** — static type checking, replacing
  mypy and pyright.
- **pytest** — tests, with asyncio support.

`script/lint` runs the same two tools over the same paths as CI, so a green run
locally means a green run on a pull request. All configuration lives in
`pyproject.toml`.

### Benchmarking

To compare compute types or decoder modes on real hardware (WER, latency, VRAM,
engine sizes). These need a CUDA GPU and the venv from `script/setup`; they
re-exec themselves into `.venv`, so the system python on the shebang line is
fine.

```bash
# One-time: build an eval set from LibriSpeech test-clean (~346 MB download,
# CC BY 4.0). Any folder of .wav/.flac files with sibling .txt transcripts
# also works.
./script/prepare_eval_set --output ./eval

# Compare compute types. Each runs in its own subprocess so VRAM numbers are
# clean; engines are cached per compute type + decoder mode under --data-dir.
./script/benchmark --model base --compute-type float16 int8 \
    --eval-dir ./eval --data-dir ./local --json results.json

# Compare decoder modes.
./script/benchmark --model base --compute-type float16 --decoder-mode kv \
    --eval-dir ./eval --data-dir ./local --json kv.json
./script/benchmark --model base --compute-type float16 --decoder-mode simple \
    --eval-dir ./eval --data-dir ./local --json simple.json

# Check which layers actually run INT8. Per-layer precision is only recorded
# when the engine was built with --detailed-build.
./script/benchmark --model base --compute-type int8 \
    --eval-dir ./eval --data-dir ./local --detailed-build --force-rebuild
./script/layer_report --model base --compute-type int8 --data-dir ./local
```
